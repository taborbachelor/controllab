ControlLab

Automated commissioning tests for industrial control logic, against a simulated line. The question it answers: can we change control software without breaking the machine?
  1. The line (left) is simulated: three bins → gates → feeder → conveyor → hopper, with the motors, switches and weigh-scale a real one has. Its control program sees only that I/O, as a PLC would.
  2. Scenarios (right) are the tests. Press Run & verify: the test operates the line, injects its fault, and checks the controller's response stage by stage against time limits.
  3. Or drive it yourself: Start/Stop below (or Manual mode, one device at a time), a guided walkthrough, or Engineer tools to break it on purpose. The status card always says what's happening, and why.
Guide to every panel
  • The plant (the picture) is a simulated bulk-material line: three storage bins, each with a gate, a feeder, a conveyor and a hopper, with the motors, limit switches, level switches and weigh-scale a real one has. A control program runs it through the same I/O a PLC would.
  • Scenarios are the tests: a setup, operator actions, a deliberate fault, the controller behavior expected at each stage with a time limit, the recovery procedure, and a PASS/FAIL verdict with every check shown expected against actual. Run & verify runs one; on the Python runtime you watch it happen on the picture.
  • Control runtime picks what runs the plant: the Python controller, the same controller as a separate program reached only over Modbus, or OpenPLC running a Structured Text port. The scenario never changes. Compare runtimes runs one scenario on each and says how they compared.
  • Controller code can swap in a deliberately broken controller (a testing fixture, never the production code) to show a regression being caught.
  • What's happening narrates the line in plain words. Guided walkthroughs let you operate it by hand, step by step. Engineer tools break the plant manually.
  • Operator holds the pushbuttons. In Auto, Start runs the whole sequence. In Manual you start and stop each device yourself: the sequence is bypassed, the protection isn't (the feeder only runs onto a moving belt, and every trip still works). The mode only changes with the line at rest.
  • Alarms and the event log record what the controller noticed and did.

      Instrument faults

      Stuck freezes the reading (a seized float, a frozen transmitter): nothing in the signal says it's wrong. Failed is a lost signal: WT-105 reads 0 with its channel diagnostic set; a switch reads 0, which the fail-safe level switches report as high. Noisy, Drifting and Slow are readings that stay plausible but wrong: nothing flags them except a cross-check or a timing check. Try LSHH-105 stuck, then set the hopper to 97 %: WT-105 still trips the line (1oo2), and the cross-check names the switch. Or make ZSS-104 slow and press Start: the belt can't prove it's moving in time.

      These act on the simulated equipment, never on the control program: the program has to notice and react on its own. A highlighted button is a fault currently injected; click it again to clear it. A motor trip also needs its device reset (Field resets) before the line's Reset will take, the same two-step recovery a real line has.
